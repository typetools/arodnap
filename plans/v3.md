# Arodnap v3 Plan

## Summary

v3 makes Arodnap a publishable, externally maintainable tool. The goal is not just broader functionality. The goal is trustworthiness:

- modernized dependencies
- explicit compatibility policy
- stable installation and upgrade paths
- release engineering discipline
- migration notes and changelogs
- fixture-backed confidence for external users

v3 treats Arodnap as a maintained product rather than a research harness with a CLI.

## v3 Objectives

- modernize the dependency stack
- define and publish compatibility guarantees
- stabilize release-grade packaging and installation
- document migration and release policies
- reduce hidden coupling between Python orchestration, Java stage tools, Checker Framework, WALA, and JavaParser

## Dependency Modernization

### Checker Framework Track

- stop treating the vendored Checker Framework directory as the long-term source of truth
- define the supported Checker Framework release line
- validate WPI behavior against the supported line
- document any remaining assumptions tied to CF internals
- distinguish between the paper-era artifact version and the supported product version

### WALA Track

- upgrade the RLFixer-side WALA integration to a newer supported line
- revalidate callgraph, classpath, and IR-sensitive logic after the upgrade
- explicitly test wrapper identification, resource classification, and fix strategy behavior

### JavaParser Track

- upgrade JavaParser in stage tools and any parser-dependent logic
- revalidate nested classes, enums, anonymous classes, and source mapping
- add tests for modern Java syntax that was uncommon in the original stack

### Java Runtime Track

- define the Java runtime required to run Arodnap
- define the supported target-project Java range
- document how older source targets are handled when the tool itself runs on a newer JDK

### Python Track

- define the supported Python version range
- split runtime dependencies from development dependencies
- make installation reproducible and auditable

## Compatibility Matrix

v3 introduces a published compatibility matrix covering:

- supported Java runtime versions for Arodnap itself
- supported target-project Java versions
- supported Gradle versions
- supported Maven versions
- supported Ant mode
- supported Checker Framework release line
- supported WALA release line
- supported JavaParser release line
- supported operating systems for official testing

Compatibility changes must be treated as release-level events and called out explicitly in release notes.

## Upgrade Policy

Major dependency families must be upgraded in controlled stages.

For each major dependency family:

1. isolate the affected adapter or tooling layer
2. upgrade one major family at a time where practical
3. run fixture-backed tests before and after the upgrade
4. compare semantic outputs, not just compilation success
5. document behavior changes and unresolved compatibility gaps

## Changelog Policy

v3 requires a structured changelog for each release with:

- Added
- Changed
- Fixed
- Deprecated
- Removed
- Breaking changes
- Migration notes

Dependency upgrades must be described in terms of behavior and support impact, not only version bumps.

## Migration Notes

Every release that changes behavior, config shape, compatibility, or supported environments must include:

- a short migration note for users
- a longer upgrade guide for maintainers and contributors
- notes about invalidated caches, patch bundles, or config changes

## Packaging And Distribution

### Required v3 Packaging

- publishable Python package for the orchestrator CLI, building on the editable
  install and console-entrypoint foundation introduced in v1.1
- clearly versioned Java stage artifacts
- stable install instructions for released versions
- stable install instructions for development builds

### Recommended Extras

- container image
- devcontainer
- `arodnap doctor`

`arodnap doctor` is introduced in v1.1. In v3 it should be extended and
polished to verify:

- Python version
- Java version
- build-tool availability where relevant
- Checker Framework availability
- stage jar availability
- temp space and filesystem access

## Publishability Requirements

v3 is not complete until all of the following exist:

- polished README for external users
- install guide
- quickstart
- supported-project matrix
- troubleshooting guide
- architecture guide
- config-file documentation
- release checklist
- citation and provenance notes where appropriate

## Testing Expectations

### Fixture Lab

Maintain a curated compatibility lab of representative repos:

- single-module Gradle
- single-module Maven
- Ant with explicit target
- multi-module Gradle leaf-module analysis
- multi-module Maven module-scoped analysis
- repo with generated sources
- repo using modern Java syntax

### Release Confidence Requirements

- end-to-end fixture tests
- golden-output tests for reports and stage outputs
- upgrade comparison tests before and after dependency bumps
- installation smoke tests for release artifacts

## Release Engineering

Use:

- semantic versioning
- tagged releases
- release notes generated from reviewed changelog entries
- traceable release artifacts

Each release must make it easy to answer:

- which dependency versions were used
- which runtime versions were tested
- which fixtures passed in CI

## Configuration Stability

If `arodnap.yaml` exists by v3, it must have a schema version and explicit validation.

Validation must report:

- invalid fields
- deprecated fields
- unsupported combinations
- ambiguous selections

Config evolution is a compatibility event and must be reflected in migration notes.

## Support Model

Document:

- how to report bugs
- what logs and manifests to include
- how to distinguish build failures from analysis failures
- how to share a minimal failing project shape

If implemented, `report-bundle` should gather:

- tool version
- runtime versions
- build system and module selection
- recent logs
- sanitized config summary

## Suggested Release Train

- `v2.1`: config schema versioning, richer manifests, formal changelog structure
- `v2.2`: staged JavaParser upgrade and parser fixture validation
- `v2.3`: staged WALA upgrade and callgraph-sensitive validation
- `v2.4`: Checker Framework integration update and compatibility-matrix refresh
- `v2.5`: packaging stabilization and release checklist
- `v3.0`: first fully publishable release with migration notes, compatibility matrix, fixtures, and polished packaging

## Acceptance Criteria

- external users can install Arodnap from docs alone
- compatibility policy is explicit and published
- dependency families are modernized and validated
- release artifacts and changelogs are disciplined and repeatable
- config and report formats are treated as stable interfaces

## Assumptions

- v1 and v2 architectural rules remain intact in v3
- dependency modernization is staged rather than done as one uncontrolled jump
- publishability includes user documentation, maintainership discipline, and release confidence, not just a successful install command
