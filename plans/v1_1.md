# Arodnap v1.1 Plan

## Summary

v1.1 is an inserted milestone between v1 and v2. It is a cleanup, hardening,
and operability release that keeps the v1 support boundary intact while making
later adapter work much cheaper and safer.

Baseline assumptions:

- `v1.0.0` is the baseline architecture and public command flow.
- validation helpers exist through `testing_v1_rulebook.md` Step 5.
- v1.1 may harden toolchain and runtime behavior, but it must stay within the
  existing v1 support boundary.

v1.1 is not a build-system expansion release. Maven, Ant, multi-module support,
and direct-classpath RLFixer integration remain later roadmap items.

## Release Theme

**v1.1 = internal architecture cleanup + operability hardening**

The milestone should make the codebase easier to reason about, debug, test, and
extend without widening supported project shapes.

v1.1 should improve:

- stage and adapter boundaries
- subprocess and environment handling
- install and debug ergonomics
- reports, manifests, and logs
- test and fixture coverage for the existing v1 contract

## Public Surface

v1.1 keeps the v1 command set and supported project shape intact, with one
intentional additive CLI command:

```bash
arodnap analyze /path/to/repo
arodnap infer /path/to/repo
arodnap repair /path/to/repo
arodnap apply --patch-dir ./arodnap-out/patches /path/to/repo
arodnap doctor /path/to/repo
```

Rules:

- no breaking change to the existing v1 commands
- `doctor` is the only additive public CLI command in v1.1
- standard single-module Gradle remains the only supported project shape
- `reanalyze(workspace)` remains the central analysis primitive
- field enhancement remains out of the public flow

## Explicit Non-Goals

These are not part of v1.1:

- Maven support
- Ant support
- multi-module Gradle support
- multi-module Maven support
- generated-source-heavy repo support
- custom source-set layout support
- direct-classpath RLFixer mode
- JavaParser, WALA, or Checker Framework major upgrade work
- changing the supported v1 project-shape contract
- rewriting the Java-based tool implementations
- publishable distribution, compatibility policy, or release engineering work

If a change does not clearly reduce the cost or risk of v2 adapter work, it
probably does not belong in v1.1.

## Goals

v1.1 should accomplish five things:

1. stabilize internal tool boundaries
2. centralize runtime and subprocess execution
3. improve developer and user operability
4. raise the test and fixture floor for the existing v1 contract
5. preserve the supported v1 behavior while making future adapter work cheaper

## Deliverables

v1.1 is done when all of the following exist:

- a shared runtime and process-execution layer
- a formal stage-wrapper base contract and stage registry
- a formal build-adapter base contract and adapter registry
- a public `doctor` command
- richer report and manifest outputs
- a basic editable-install plus `arodnap` console-entrypoint story
- stronger unit, fixture, and integration coverage for the v1 scope
- docs updated to explain the v1.1 architecture and usage

## Workstreams

### A. Runtime Layer Consolidation

Objective: remove duplicated subprocess, timeout, environment, and log-capture
logic from adapters, analysis runners, stage wrappers, and patching code.

Deliverables:

```text
arodnap/runtime/
  __init__.py
  commands.py
  environment.py
  java.py
  timeouts.py
  errors.py
  logging.py
  patching.py
  versions.py
```

Required behavior:

- one subprocess runner abstraction with consistent result objects
- one timeout source of truth
- one command-rendering and log-header format
- shared environment shaping for Gradle, WPI, Java tools, and patch execution
- shared lightweight version probes for Python, Java, Gradle, patch, and
  Checker Framework path sanity

Acceptance criteria:

- no new direct `subprocess.run(...)` outside runtime utilities unless
  explicitly justified
- process failures produce one consistent error style
- command logging and capture are consistent across adapters and stages

### B. Stage Wrapper Cleanup

Objective: make all stage wrappers follow one consistent contract and execution
shape.

Deliverables:

```text
arodnap/stages/
  base.py
  registry.py
  close_injector.py
  owning_field.py
  rlfixer.py
  rlpatcher.py
```

Introduce a lightweight `BaseStageWrapper` or equivalent protocol with shared
structure for:

- `name`
- `validate_inputs(...)`
- `invoke_tool(...)`
- `normalize_outputs(...)`
- `validate_outputs(...)`
- `run(...)`

Wrapper rules:

- accept only normalized Arodnap inputs
- invoke tools through shared runtime helpers
- emit normalized outputs under the stage directory
- write `stage_result.json`
- never decide pipeline order
- never rerun analysis directly
- never guess build information
- never leak raw tool-specific patch paths past the wrapper boundary

Acceptance criteria:

- stage execution order is owned by a registry or equivalent orchestration layer
- every stage writes structured outputs in one style
- no wrapper leaks old benchmark-layout assumptions outside its own boundary

### C. Build Adapter Hardening

Objective: keep Gradle as the only supported backend while cleaning the adapter
boundary so future Maven or Ant adapters fit naturally.

Deliverables:

```text
arodnap/build_adapters/
  __init__.py
  base.py
  registry.py
  gradle.py
```

Required additions:

- a stable adapter contract suitable for later non-Gradle adapters
- a small adapter registry, even if Gradle is the only registered adapter
- richer adapter metadata including:
  - selected build tool
  - compile target
  - source root
  - compiled classes root
  - classpath file path
  - whether the wrapper or system `gradle` was used

Acceptance criteria:

- pipeline code does not hardwire Gradle-specific logic beyond adapter selection
- Gradle remains the only supported backend in v1.1
- unsupported-project failures become more structured and more diagnosable

### D. `doctor` Command

Objective: add a user-facing prerequisite and supportability check.

Public CLI:

```bash
arodnap doctor /path/to/repo
```

`doctor` should validate:

- Python availability and version
- Java availability and version
- Gradle wrapper or `gradle` on PATH
- patch binary availability and flavor
- vendored Checker Framework path
- required plugin jars
- repo-shape support for v1
- `src/main/java` existence
- compile-target viability
- any known WPI Python/runtime prerequisites that can be checked cheaply

Output requirements:

- human-readable terminal summary
- machine-readable JSON, for example `arodnap-out/doctor.json`

Each check should include:

- `name`
- `status`: `ok | warning | error`
- `message`
- optional `details`

Acceptance criteria:

- `doctor` succeeds on supported repos
- `doctor` fails clearly on unsupported repos
- common environment problems are diagnosed before users reach `repair`

### E. Report, Manifest, and Logging Improvements

Objective: make outputs more useful for debugging and support without
redesigning the v1 output contract.

Rules:

- preserve output compatibility where practical
- prefer backward-compatible field additions over format redesign

Expected additions where appropriate:

- tool version
- command
- repo root and workspace root
- build args and compile target
- adapter name and selected build tool
- Java version
- patch binary and patch flavor
- timestamps and elapsed durations
- stage durations and analysis labels
- warning counts per analysis point
- environment snapshot summary
- explicit error classification

Logging should standardize:

- tool name
- command
- cwd
- timeout if any
- exit code
- stdout
- stderr

Acceptance criteria:

- failures can be debugged from artifacts more often without immediate reruns
- `manifest.json`, `report.json`, and stage logs remain machine-readable and
  coherent

### F. Packaging and Installability

Objective: make the repo feel like a real tool checkout without pulling
publishable packaging work out of v3.

Allowed v1.1 packaging scope:

- `pyproject.toml` or equivalent modern Python packaging metadata
- editable install support
- console entrypoint `arodnap`
- dependency grouping for runtime vs dev or test
- install and contributor setup docs

Out of scope for v1.1:

- release-grade distribution
- compatibility matrix
- release engineering
- polished publishable artifacts

Acceptance criteria:

- a clean editable dev setup exists
- a user can install and run `arodnap`
- docs prefer `arodnap <command> ...` over `python -m arodnap.main ...`

### G. Test and Fixture Hardening

Objective: raise the confidence floor before v2 refactors and adapter work.

Required outcomes:

- stronger unit tests around contracts, wrapper boundaries, patch handling, and
  report generation
- fixture-backed integration coverage for the current v1 contract
- golden checks for `report.json`, `manifest.json`, and `stage_result.json`

Implementation note:

- do not require a disruptive test-suite reorganization before refactors
- incremental adoption under the current `tests/` tree is acceptable
- adding `tests/unit/` and `tests/integration/` is allowed when it helps, but
  it is not a prerequisite for every v1.1 change

Acceptance criteria:

- core v1 behavior keeps regression coverage during refactors
- future Maven and Ant work has a stable v1 baseline to compare against

### H. Documentation Cleanup

Objective: make docs match the real implementation and the v1.1 operator story.

Required updates:

- install instructions
- `doctor` usage
- troubleshooting guidance
- workspace-copy explanation
- patch and apply model
- supported and unsupported scope
- output-artifact overview
- contributor architecture notes for runtime, adapter, and stage boundaries

v1.1 should also produce a short release-note draft, but release discipline and
publishable release engineering remain v3 concerns.

## Suggested Milestones

### Milestone 1: Runtime and Wrapper Foundation

- add the runtime package
- move duplicated subprocess logic into runtime helpers
- add stage-wrapper base behavior
- add stage registry
- preserve behavior

### Milestone 2: Adapter Hardening

- introduce adapter registry
- improve adapter metadata
- clean the adapter contract
- keep Gradle only

### Milestone 3: `doctor`

- add the command
- add JSON output
- add README usage

### Milestone 4: Reporting and Packaging

- enrich report and manifest outputs
- add editable-install metadata
- add the `arodnap` console entrypoint
- update install docs

### Milestone 5: Tests and Fixtures

- add unit and integration coverage for the current v1 contract
- add golden output checks
- stabilize the regression story before v2 expansion

## Acceptance Criteria

v1.1 is complete when:

- supported single-module Gradle behavior from v1 still works
- `doctor` exists and is useful on supported and unsupported repos
- subprocess execution is centralized
- stage wrappers have a unified structure
- the Gradle adapter fits a future adapter model
- editable install plus `arodnap` entrypoint exist
- report and manifest outputs are richer without unnecessary breakage
- test and fixture coverage is stronger for the current v1 contract
- no new build-system support is introduced in this release

## Codex Execution Guidance

- do not widen public support scope
- refactor in small, behavior-preserving steps
- do not rewrite Java tool logic
- keep legacy assumptions isolated to one owner where they still exist
- preserve machine-readable output compatibility where practical
- add tests as runtime, wrapper, and adapter cleanups land

The key question for every v1.1 change is:

**Does this cleanup make future adapter work cheaper without widening support
scope?**

If yes, it belongs in v1.1. If not, it probably belongs later.
