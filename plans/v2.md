# Arodnap v2 Plan

## Summary

v2 expands Arodnap from a narrow v1 Gradle tool into a robust multi-build, multi-shape analysis system with stronger recovery, configuration, observability, and patch management. The architectural rules from v1 remain fixed:

- Python owns the pipeline.
- Java owns analysis and transformation logic.
- `reanalyze(workspace)` remains the universal analysis primitive.
- The original repo is not mutated by default.
- RLFixer compatibility remains automatic and hidden from the user.

v2 begins after the v1.1 cleanup milestone. It is about build-system breadth,
module selection, and project-model expansion, not an architectural reset.

## Scope

### New Supported Project Types

- single-module Maven
- standard Ant projects with explicit compile targets
- multi-module Gradle with module selection
- multi-module Maven with module selection

### New Operational Capabilities

- checkpoints and resumable runs
- richer config and overrides
- structured failure handling
- stronger patch preview and apply workflows
- project-model-aware reports and diagnostics on top of the v1.1 baseline

## Project Model

v2 introduces a shared internal project model used by all adapters. It must represent:

- repository root
- modules
- selected analysis scope
- module dependency graph
- source roots per module
- output directories per module
- dependency classpath entries per module

The project model is backend-neutral. Gradle, Maven, and Ant adapters all populate the same shape.

## Build Adapters

### Maven Adapter

The Maven adapter must support:

- conventional single-module Maven projects
- source discovery from the standard main Java source root
- dependency and output classpath extraction
- WPI invocation using the official Checker Framework flow
- compatibility bundle generation for RLFixer

### Ant Adapter

The Ant adapter is explicitly configuration-backed. It must support:

- standard Ant repos with a clear compile target
- explicit target override in config or CLI when needed
- classpath and output discovery through adapter-controlled conventions or explicit config

### Multi-Module Gradle

The first multi-module Gradle release should support one selected leaf module at a time.

Rules:

- the selected module is the only source tree mutated in the workspace
- upstream dependent module outputs may be used in the classpath
- Arodnap does not attempt a repo-wide multi-module mutation strategy in v2

### Multi-Module Maven

Use the same model as multi-module Gradle:

- analyze one selected module at a time
- compile dependent modules as needed
- generate module-scoped RLFixer compatibility inputs

## Configuration

v2 introduces `arodnap.yaml`.

### Configuration Capabilities

- build system override
- module selection
- compile target override
- source-root override
- class-output override
- dependency classpath override
- WPI build arguments
- RLFixer compatibility settings
- stage enable and disable controls
- timeout values
- memory limits

### Precedence Rules

- conventions first
- config second
- one-off CLI overrides third

The tool must fail clearly when automatic detection is ambiguous and no explicit config resolves it.

## Failure Resistance

### Workspace Isolation

- continue to operate in a temporary workspace by default
- support persistent workspace retention with `--keep-workspace`
- preserve enough metadata to reproduce a failed run

### Checkpointing

Save state after each major transition:

- after initial analysis
- after every stage that can change sources
- after every reanalysis
- after RLFixer
- after RLPatcher

Each checkpoint must include:

- current workspace pointer
- latest diagnostics path
- latest inference directory
- stage history
- run manifest

### Resume

Add resumable execution using the checkpoint metadata. Resuming must not require recomputing earlier successful stages unless the workspace or config has changed.

### Timeouts And Resources

Add:

- per-stage timeouts
- per-build timeouts
- configurable Java heap settings for tool invocations
- graceful shutdown with explicit timeout errors

### Structured Errors

Define an error taxonomy with distinct categories:

- build failure
- WPI failure
- checker failure
- stage failure
- RLFixer failure
- patch materialization failure
- patch apply failure
- unsupported project shape

Every failure must capture:

- failing command
- exit status
- stderr summary
- relevant log path
- stage or adapter name

## Observability

v2 extends the v1.1 report and manifest baseline with project-model,
checkpointing, and resume-aware observability.

### Required Output Additions

- top-level `report.json`
- per-stage `stage_result.json`
- run manifest with adapter and project-model data
- checkpoint metadata files
- concise end-of-run summary output

### Optional Future-Friendly Outputs

- markdown summary
- HTML report

If added, these are views over the machine-readable artifacts, not separate sources of truth.

## Patch Handling

### Patch Preview

Add a non-applying patch preview mode that reports:

- which files would change
- which stage produced each patch
- whether patches supersede earlier stage-local changes

### Patch Bundles

Emit:

- one patch bundle per stage
- one final combined patch bundle

### Patch Manifest

The patch manifest must record:

- patch path
- originating stage
- target root
- strip level
- affected files
- whether a later patch superseded the change

### Safer Apply Flow

The apply path must support:

- dry-run validation
- stage-scoped apply
- full-bundle apply
- failure reporting with the exact patch that failed

## RLFixer Evolution

v2 still allows the compatibility bundle, but begins the cleanup path.

### Required v2 Work

- isolate compatibility bundle generation behind a stable interface
- stop leaking normalized-layout assumptions outside `compat/`
- prepare a direct classpath-based RLFixer wrapper path behind a non-default interface

### Not Yet Required

- removing the compatibility bundle entirely

That belongs only after the direct classpath path is proven stable.

## Testing And CI

### Fixture Matrix

Add fixtures for:

- single-module Gradle
- single-module Maven
- Ant with explicit compile target
- multi-module Gradle selected-module analysis
- multi-module Maven selected-module analysis
- one project with generated sources or explicit source-root overrides

### CI Requirements

- unit tests for all adapters
- integration tests across fixture repos
- serialization checks for reports and stage outputs
- resume-from-checkpoint tests
- patch preview and apply tests

## Acceptance Criteria

- v2 supports Maven and Ant without changing the v1 architecture.
- v2 supports module-scoped multi-module analysis for Gradle and Maven.
- resumable execution works from machine-readable checkpoints.
- failures are categorized and diagnosable without reading raw logs first.
- patch preview and patch manifests are stable enough for users and future integrations.

## Assumptions

- v1 is complete and stable before multi-build support expands.
- Module-scoped analysis is the only supported multi-module strategy in v2.
- The direct-classpath RLFixer path may begin behind a feature flag, but the compatibility bundle remains the default until validated.
